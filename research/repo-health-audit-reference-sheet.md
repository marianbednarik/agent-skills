# Codebase audit: rethink of repo-health-audit

Research date: 27 September 2026. Scope: the canonical `skills/repo-health-audit` skill, its agreed rename to `codebase-audit`, and this supporting research. Status: compact redesign and rename adopted after direction agreement, six matched probes, independent comparison, and structural validation. External instructions are research material, not local authority.

## Intent and baseline

Marián wants both an overall understanding of structural health and help deciding what is worth improving next, including removing needless complexity (“unslopify”), maintainability, and performance. No concrete failure transcript was supplied. He questioned mandatory HTML and explicitly preferred letting the agent use inline diagrams and custom interactive visuals in conversation. He agreed to rename the skill to `codebase-audit`, retain assessment as the default, implement when requested, and choose richer artifacts according to need.

The original is preserved at Git commit `bb685eac37591e2fac0e697904a93f41b34e38c4`, path `skills/repo-health-audit/SKILL.md`, blob `e3f40678ea77883713f65ccdc6291f658f6b1261`. Recover it with `git show bb685eac:skills/repo-health-audit/SKILL.md`. The working file matched that version at the start. The unrelated untracked `research/skill-stack-reference-sheet.md` was present and is outside this work. `~/.agents/skills/repo-health-audit` was a symlink to the canonical directory; renaming must preserve the existing installation under the new name, without introducing a duplicate skill. Other model variants and global guidance are outside scope.

The baseline's purpose is already decision-oriented: choose worthwhile maintenance, explain its cost and benefit, and distinguish confidence in a problem from confidence in a fix. It authorizes investigation/reporting and implementation only when requested. It samples hotspots and representative paths, warns against treating its concern list as a checklist, requires concrete references and prevalence checks, and allows little to change. These are strengths to preserve.

Possible gaps were hypotheses, not observed failures: “health” can suggest an exhaustive certification; hotspot guidance leaves the relationship to actual change cost implicit; the concern list omits performance; the three recommendation buckets overlap urgency and ease; there is no explicit test of whether consumers or constraints invalidate a cleanup; and substantial audits must create HTML regardless of whether that helps the owner. Most desired improvements are already compatible with the baseline, so superiority must not be assumed.

Neighboring ownership: `check-work` assesses completed changes and affected behavior, excluding unrelated pre-existing maintenance. `shaping` supports open design choices, while an audit should usually reach recommendations. `project-context` preserves agreed intent; an audit consumes that context rather than silently changing it to match code. The runtime skill need not invoke any of these to do its job.

## Methods, empirical evidence, and counterweights

| Primary source | Evidence and useful mechanism | Limits on adaptation |
| --- | --- | --- |
| [Tornhill, Code as a Crime Scene (2013)](https://accu.org/journals/overload/21/117/tornhill_1835/) and [CodeScene hotspots, version 6.6.12](https://docs.enterprise.codescene.io/versions/6.6.12/guides/technical/hotspots.html) | Professional method: combine development activity with complexity and change coupling to choose areas worth inspecting. | Activity is an attention filter, not a diagnosis. Cold code may still matter for runtime cost; new or squashed histories may be unrepresentative. No need to install a tool or calculate a universal score. |
| [Nagappan and Ball, relative churn (2005)](https://www.microsoft.com/en-us/research/publication/use-of-relative-code-churn-measures-to-predict-system-defect-density/) | Windows Server 2003 study found absolute churn a poor predictor while relative measures performed better in that setting. | Does not establish thresholds for personal projects, prove causation, or rank maintenance value. Supports checking what a metric represents before drawing conclusions. |
| [Kim, Zimmermann, and Nagappan, Microsoft refactoring study (2014)](https://www.microsoft.com/en-us/research/publication/an-empirical-study-of-refactoring-challenges-and-benefits-at-microsoft/) | Survey, interviews, and history analysis. Preferentially refactored modules reduced dependencies and several complexity measures while increasing size; developers reported cost and risk. | Multidimensional assessment matters; fewer lines is not a success measure. Industrial Windows work does not validate our prompt or establish the payoff for a prototype. |
| [Google, architectural complexity, maintenance burden, and developer sentiment](https://research.google/pubs/understanding-architectural-complexity-maintenance-burden-and-developer-sentiment-a-large-scale-study/) | Large-scale observational study connects architectural complexity with maintenance burden and developer experience. | Correlation is not causation, and enterprise evidence transfers imperfectly. Use concrete responsibilities and change paths rather than aesthetics or ungrounded architecture scores. |
| [Fowler, Technical Debt (2019 revision)](https://martinfowler.com/bliki/TechnicalDebt.html) | Explains repayment in relation to repeated future change cost, while acknowledging weak precision in estimates. Stable awkward code can reasonably be left alone. | Borrow qualitative payoff and timing. Do not fabricate hours saved or require a financial business case for every useful cleanup. |
| [Fowler, Opportunistic Refactoring (2011)](https://martinfowler.com/bliki/OpportunisticRefactoring.html) | A credible alternative to audit-driven maintenance: make small improvements alongside actual feature work; prepare code when it helps an imminent change. Warns about rabbit holes and weak regression protection. | Audits still help identify cross-cutting issues and restore understanding. Recommendations need not become standalone projects; defer a small cleanup to the next relevant change when appropriate. |
| [Gregg, Performance Analysis Methodology](https://www.brendangregg.com/methodology.html), evolving summary of methods presented from 2012 | Start from a performance question and workload, drill down with relevant measurements, and choose methods based on what remains uncertain. Describes failure modes of random tool use and passive benchmark reports. | Borrow workload relevance and targeted evidence, not a systems-engineering checklist or compulsory profiler run. Static code can demonstrate repeated I/O without establishing production latency or a precise speedup. |

None of these sources establishes that a longer skill improves agent behavior. The useful adaptation is specific: select representative paths, investigate observable friction, consider counterevidence, and recommend changes according to actual consequence and uncertainty.

## Alternatives and agreed direction

| Option | Strongest case | Tradeoff |
| --- | --- | --- |
| Retain baseline, edit only reporting | Compact and already sensible; little regression risk | Leaves performance and overall structural explanation implicit despite the clarified use case |
| Broader `codebase-audit` with compact decision guidance | Covers understanding, simplification, maintainability, and proportionate performance; remains assessment-first | Can drift into a universal audit if concern examples become a checklist; retain sampling and scope judgment |
| Cleanup-first `improve-codebase` | Directly removes low-value code and avoids findings backlogs | Changes authority and primary outcome; the owner chose assessment with implementation when requested |
| Fold into `check-work` or ordinary prompting | Reduces skill count and duplicate general principles | Loses an explicit place for accumulated repository-wide issues outside a completed change; no current evidence justifies retirement |

Marián selected the second option. `codebase-audit` names the inspected subject and activity without implying a runtime “health check.” `deslop` would be too narrow and aesthetic; `maintenance-review` underplays performance and resembles change review. The new description retains the boundary with completed-change review and specific-bug diagnosis.

Preserve practical evidence, maturity calibration, useful foundations, no-findings success, separate confidence in problem and remedy, grouping of shared causes, and the audit/remediation distinction. Add proportionate structural orientation, consumers/constraints as counterevidence, performance evidence, a concrete success check for recommendations, and an explicit completion condition. Replace fixed urgency/ease buckets with reasoned priority; do not require scores, a finding count, or exhaustive coverage.

Reporting decision: lead in chat with overall condition and the next move, explaining the important relationships. Inline diagrams and custom interactive visuals are available when they help understanding or comparison. A separate durable artifact must earn its place through a requested use or saving/sharing/revisiting value. HTML remains possible, with no automatic HTML requirement. Observed structure and proposed changes remain visibly distinct.

## Matched behavioral comparison

Six fresh GPT-6 Sol agents at medium reasoning effort received one of three isolated project fixtures and either the original or candidate guidance. Within each pair, project contents, prompt, model settings, and harness restrictions were equivalent. These are execution-after-loading probes: agents were instructed to load the assigned body. They do not test discovery or automatic skill selection. The skill names differ as part of the tested revision; inherited platform instructions and available skill descriptions remain common.

The harness forbids reading outside the assigned run directory, loading other skills, or delegating. It permits normal investigation and project commands, and permits report artifacts beside the project. It requires saving the final response for comparison. It supplies no expected findings, performance caveat, cleanup warning, or private evaluation criteria. Exact fixtures, prompts, assigned versions, and results are preserved in `repo-health-audit-probes.json`.

| Scenario | Ordinary request and discriminating evidence |
| --- | --- |
| Structural maintenance | Small booking app; duplicated pricing in two active paths; legacy CSV and provider adapter have documented live purposes; intended membership work and partial tests expose uncertainty. Does the audit find useful consolidation without deleting meaningful boundaries? |
| Performance | Local asset board; per-asset label I/O; a runnable simulated-latency benchmark; rare export sorting. Does the audit distinguish concrete redundant work, simulated timing, real-environment uncertainty, and optimization that is not worth doing? |
| Little worthwhile work | Small stable CSV reading script; low workload, no planned expansion, useful tests. Does the audit finish without manufacturing an architecture or optimization project? |

Private assessment concerns: useful prioritization; appropriate scope; preserved compatibility; unsupported claims; evidence quality; user effort; reporting overhead; and whether enough investigation is recognized. These are synthetic, small projects with straightforward context and little history. Similar outcomes must be reported honestly. They do not establish real-world reliability, large-repository coverage, or personal fit of interactive reports.

## Independent assessment and completion

A fresh GPT-6 Astra agent at high effort received A and B with equivalent paragraph formatting, no conversation history, no age labels, no research or preferred verdict. A is the candidate and B the baseline. Its task is to compare strengths, losses, ambiguities, and likely upgrades/downgrades against neutral requirements. This text review is separate from behavioral evidence.

The independent reviewer preferred A against the stated requirements: explicit overall structure, substantive performance evidence, consumer/constraint checks, a success check for recommendations, and reporting proportional to use. It identified losses in brevity and fixed action categories, but judged the flexible priority criteria a reasonable tradeoff. Its one concrete correction was to restore “Follow the requested scope” alongside the investigation guidance. That sentence was added; no other behavior changed after the probes. No further review round was warranted for that narrow clarification.

### Final implementation and validation

The canonical skill is now [skills/codebase-audit/SKILL.md](../skills/codebase-audit/SKILL.md). Its name and description match the new scope. The runtime symlink was migrated from `~/.agents/skills/repo-health-audit` to `~/.agents/skills/codebase-audit`, preserving the existing installation without an alias or duplicate. Historical research references retain the original name because they describe the skill at that time. No other skills, model variants, global configuration, commits, or pushes were changed.

The baseline was 399 whitespace-separated words including frontmatter; the final skill is 560. The increase buys structural orientation, performance evidence, consumer checks, stopping, and flexible visual reporting. No runtime support files or mandatory tools were added. Paragraphs are not manually wrapped.

The skill validator passed with `uv run --no-project --with PyYAML python /Users/marian/.codex/skills/.system/skill-creator/scripts/quick_validate.py skills/codebase-audit`, and `git diff --check` passed. System and bundled Python lacked PyYAML; an isolated uv dependency environment resolved the validator dependency without changing the project environment. Source/name consistency, runtime symlink resolution, and references were checked. The unrelated pre-existing `research/skill-stack-reference-sheet.md` was preserved.

Remaining uncertainty: automatic discovery under the new name, larger or messy repositories with incomplete context, useful prioritization when many plausible issues compete, remediation continuation, and whether richer inline reports improve Marián's actual understanding. Observe those in real use before adding more rules or evaluation machinery. The current evidence supports a better fit to clarified intent while preserving competent baseline behavior, not a proven reliability gain.
